# Generator v0.2 foundation design

Date: 2026-09-22

## Scope

Generator v0.2 establishes the deterministic and exact foundation required before large-scale difficulty research.

This phase covers:

1. exact puzzle canonicalization independent of displayed color names and tube order;
2. deterministic seeded candidate generation and reproducibility metadata;
3. exact minimum-empty-tube semantics;
4. per-candidate solver resource guards and sequential execution.

Difficulty Model v2, mistake/recovery analysis, quality filtering, and production-scale catalog generation are intentionally deferred until this foundation is stable.

## Core model

The generator does not own presentation colors.

A puzzle contains abstract types only:

- Type identity has no user-visible meaning.
- A runtime client may map Type 0..N to any palette.
- Retry may use a different palette without changing level identity.
- Reload should preserve the runtime palette seed if visual continuity is desired.

The generator therefore solves and deduplicates only structural type layouts.

## Limits

Initial engineering target:

- capacity: 4;
- type count: up to 16;
- empty-tube search: sequential from 1 upward;
- execution: one candidate at a time by default.

The type-count ceiling is not a gameplay recommendation. It is an encoding/benchmark target. Consumer applications may impose lower UI limits.

## Deterministic generation

All generator randomness must come from an explicit versioned PRNG. Unseeded randomness such as Math.random() is forbidden in generation code.

A batch is identified by:

- generatorVersion;
- rngVersion;
- canonicalVersion;
- encodingVersion;
- config fingerprint;
- batchSeed.

Each candidate is independently derived from:

```text
candidateSeed = derive(batchSeed, profile, difficulty, candidateIndex)
```

A candidate must not depend on how many random values previous candidates consumed.

Required reproducibility property:

```text
same generator version
+ same config
+ same batch seed
+ same candidate index
= same raw candidate
= same normalized/canonical puzzle
= same solver result
```

Audit data records the reproducibility metadata. Runtime Level Packs do not need authoring seeds.

Stable level IDs encode the generator, RNG, and rules versions plus batch seed,
profile, difficulty, capacity, and candidate index. The batch seed encoding is
reversible, so distinct batches cannot reuse an ID for different boards. IDs
do not depend on the accepted-list position.

## Exact type normalization

Displayed colors are outside puzzle identity.

Canonical type IDs are assigned by first occurrence while scanning a candidate tube ordering from bottom to top:

```text
first unseen raw type  -> canonical Type 0
next unseen raw type   -> canonical Type 1
...
```

The mapping is global to the entire puzzle. It must never be reset per tube.

Per-tube offset normalization is invalid because it destroys cross-tube type relationships and can cause distinct puzzles to collide.

## Tube encoding

A tube is encoded into a bigint-backed unsigned 64-bit value.

For capacity 4 and at most 16 types:

- each type cell requires 4 bits;
- four cells require 16 bits;
- length/occupancy requires 3 bits;
- remaining bits are reserved.

Numeric ordering must match bottom-to-top lexicographic ordering of canonical type IDs.

The exact bit layout is versioned as:

```text
encodingVersion = "tube64-v1"
```

JavaScript Number is not used for uint64 identity because it only provides 53 bits of integer precision.

## Tube-order canonicalization

Puzzle identity ignores tube order.

For a partial canonicalization state:

1. keep one shared global raw-type -> canonical-type mapping;
2. tentatively encode each remaining tube using that mapping;
3. unseen raw types receive the next canonical IDs in bottom-to-top order;
4. find the minimum candidate tube encoding;
5. if exactly one distinct remaining tube shape produces the minimum, commit it;
6. if multiple distinct tube choices tie, branch only across those tied choices;
7. identical remaining tube shapes are represented as a multiset count and expanded only once;
8. tied tubes whose as-yet-unmapped Types occur in no other remaining tube are equivalent under raw-Type renaming, so expand one representative;
9. continue until all tubes are consumed;
10. choose the lexicographically smallest complete encoded tube sequence.

Branches whose prefix is already lexicographically greater than the best complete sequence may be pruned.

Equivalent recursive search states should be memoized where practical.

The private-Type tie rule is exact only when every Type in the candidate tube is
unmapped and appears in no other remaining tube. Those Types have no future
cross-tube relationships to distinguish which tied tube was chosen. This avoids
factorial branching on boards with many isolated uniform Types; a regression
test covers 16 isolated Types, and exhaustive small-board comparisons protect
the canonical result.

The output is an exact canonical sequence:

```text
bigint[]
```

This sequence, not a hash, defines puzzle equality.

Version:

```text
canonicalVersion = "tube-order-v2"
```

## Dedup index

Canonicalization and storage are separate concerns.

The current implementation stores canonical sequences in an exact trie keyed by encoded tube values. Each tube code is one child key; a terminal leaf marks a previously accepted complete sequence.

Canonicalization and storage remain separate concerns, so a future benchmark may replace the trie with a hash index plus exact sequence comparison if that materially reduces memory. No probabilistic hash-only equality is allowed.

## Minimum empty tubes

For a fixed shuffled full-tube arrangement, test empty-tube counts in ascending order:

```text
1 empty
2 empty
3 empty
...
```

Solver result semantics are strict:

- solved: a solution has been found;
- unsolvable: the reachable search space has been exhausted within an exact search and no solution exists;
- budget-exceeded: unknown.

If all counts below k are proven unsolvable and k is solved:

```text
minimumRequiredEmptyTubes = k
```

If any smaller count returns budget-exceeded, the exact minimum is unknown even if a larger count is solved.

Unknown minimum candidates are rejected from production-quality output rather than mislabeled.

Because adding an unused empty tube cannot remove an existing solution, solvability is monotonic with respect to empty-tube count.

## Solver roles

Feasibility/proof and optimal-path analysis are logically separate tasks.

During empty-tube search:

- prove unsolvability for smaller empty counts;
- stop at the first proven-solvable count;
- finding any solution is sufficient for feasibility.

After a candidate is accepted:

- run optimal-path analysis when needed;
- compute minimum moves and later difficulty metrics.

The current A* implementation may initially serve both roles, but APIs and result semantics must preserve this separation.

## Resource guards

Generator v0.2 defaults to one worker and sequential candidate processing.

Each solver invocation has explicit limits such as:

- max unique visited/discovered states (memory-oriented guard);
- max search depth;
- optional elapsed-time guard when implemented.

A guard hit produces budget-exceeded, never unsolvable.

Pathological candidates are rejected instead of allowing one candidate to dominate the batch.

Solver search data must be candidate-local and releasable before processing the next candidate.

Long-running research may later use worker process recycling to ensure OS-level memory reclamation.

## Required tests

Canonicalization tests must include:

- pure type renaming equivalence;
- tube reordering equivalence;
- empty-tube reordering;
- repeated identical tubes;
- adversarial cases where per-tube normalization would create a false collision;
- structurally different puzzles that use the same per-tube local patterns;
- deterministic canonical output across repeated runs.

Determinism tests must include:

- same seed/config/index -> same candidate;
- different candidate indices do not depend on prior RNG consumption;
- same candidate reproduces directly from its audit metadata.

Minimum-empty tests must include:

- 1 empty solved -> minimum 1;
- 1 empty proven unsolvable, 2 solved -> minimum 2;
- smaller budget-exceeded, larger solved -> minimum unknown;
- search stops after the first exact solved count.

## Deferred v0.2 follow-up

After this foundation is stable:

1. benchmark 6..16 types;
2. record p50/p90/p95/p99 solver states, time, and memory;
3. implement mistake/recovery analysis;
4. implement quality filtering;
5. build a human-calibrated difficulty benchmark set;
6. produce a production catalog.


## Optimal solution retention

Every accepted production-quality puzzle must retain both:

- `optimalMoves`: the proven shortest move count;
- `optimalSolution`: one complete move sequence whose length equals `optimalMoves`.

These values are authoring facts and must survive catalog generation so they can support:

- player challenge modes against the optimum;
- hint/replay systems;
- regression verification;
- analytics and difficulty research;
- alternate clients and future gameplay modes.

The standard Runtime Level Pack should expose `optimalMoves` but should not embed the full `optimalSolution` by default, because shipping the full answer with every puzzle makes extraction trivial.

The generator therefore supports a separate exact solution artifact keyed by stable level ID:

```json
{
  "formatVersion": 1,
  "rulesVersion": "classic-v1",
  "solutions": [
    {
      "id": "ws-v1-h-000001",
      "optimalMoves": 37,
      "optimalSolution": [
        { "from": 2, "to": 8, "color": 4, "amount": 1 }
      ]
    }
  ]
}
```

A consumer that genuinely needs full solutions may ship or fetch this artifact separately. The normal gameplay pack remains answer-free except for the optimal move count.

The validator must replay every stored optimal solution and verify:

1. every move is legal under the declared rules;
2. the final board is solved;
3. `optimalSolution.length === optimalMoves`.

The current A* solver is responsible for producing a shortest solution; solver correctness tests must continue to protect that contract.


## Packed solver state

The authoring solver uses a separate compact state encoding from puzzle canonicalization.

For capacity <= 4 and type IDs 0..15:

- each cell uses 5 bits;
- stored cell value 0 means unused/empty slot;
- stored values 1..16 represent Type 0..15;
- one tube therefore uses 20 bits and fits in a uint32;
- one solver board is a fixed-length array of packed tube codes.

Solver-state identity ignores tube order but preserves type identity within one search:

```text
packed board
-> sort packed tube codes
-> concatenate 20-bit codes into one bigint key
```

The tube count is included in the key prefix so the representation is exact even outside a fixed solve.

This encoding is versioned independently from the cross-puzzle canonical representation:

```text
solverStateEncodingVersion = "packed-tube20-v1"
```

Search nodes retain packed tube arrays rather than nested JavaScript arrays, and the visited map uses bigint keys rather than serialized strings. Public rule validation remains based on the ordinary Board/Move model so exported solutions can still be replayed independently.

The packed implementation must be behaviorally equivalent to classic-v1 rules. Tests compare packing round-trips, legal moves, solved-state detection, and known shortest solutions.
